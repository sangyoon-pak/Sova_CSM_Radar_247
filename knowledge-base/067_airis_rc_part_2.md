AIRIS uses an IP geolocation service to estimate the location of the device doing the actions that make up a given visit. Geolocation can be very precise in some cases, and very imprecise in others. Sometimes a visit is coming from a serverside tracking event, and the original client device's IP has not been passed along to AIRIS. AIRIS will then use the IP of whatever device sent us the track request, and that IP will belong to a server in a data center in Dallas, Texas while the user is sitting in a coffee shop in Milwaukee.

Note the longitude and latitude values are not precise. They will usually be the center point of a given city or neighborhood, and are most useful in calculating "nearby" users (as numbers that can be passed to geography API's, etc.)

(duration)

Visit duration is simple in concept, but can become very complex as you consider atypical cases. In its simplest form, Visit duration is the length of time between the first event and the end of the timeout after the last event. By default, a web visit session will time out after the user has been idle for 5 minutes. This is calculated using event times and event durations.

The perfect example of this working is in a browser session tracked by our SDK. The browser tracker makes full use of server pinging, sane default event timeouts, etc. What this means is that every event tracked by our tracker has a duration, and the visit duration is quite simply the sum of the event durations of the events that make up the visit.

It gets more complex with serverside events, events brought in by AppConnect apps from other services, and in general, anything not tracked by our tracker in the browser. Certain events have a 0 duration. Other times, it is easy to accidentally send explicit event durations with each event that are actually overlapping, and thus artificially inflating your visit duration. It is also worth noting that the /ping requests will automatically be applied to the latest active, non-system event. See Generated Event Properties for the list of system events.

System Event Properties [1]

https://docs.airis.appier.com/docs/generated-action-properties



There are three event types in AIRIS: Active, passive, or system. When defining event schema, you can set the event type to either active or passive.

Active: Set the event to Active if this event is sent as a result of an action the user takes. For example, the user makes a purchase, clicks a button, or opens an email campaign.

Passive: Set the event to Passive if it's a serverside action or background event that is tracked on the user's behalf. For example, the user receives an email or is shown an in-web campaign.

System: These are system-generated events. Property update, segment join, and segment leave are system events.

Defining the event types allows you to filter based on event types when creating segments or generating reports. For example, you can generate a profile report of your monthly active users by including users who did an active event in the last 30 days.

Tips for Tracking in Single Page Applications

Installing tracking code in Single Page Applications (SPAs) is slightly more complicated in that you cannot simply copy the tracking code and paste it into your page's section. This is because the idea of a SPA is that the page head is not reloaded all the time, but rather just parts of the page are updated based on data-only (not full page HTML) requests made in the background.

If you have developers implementing custom event tracking, you shouldn't have a problem with this, as an SPA developer should be intimately familiar with this issue as it's core to the concept of SPA's.

You'll probably still want to load the Web SDK code snippet in your page's section though you'll be unable to track all of your users' behavior if you simply put your tracking code in the section, because it will only run once at page load, and subsequent actions taken by the user in your web app will not be automatically re-tracked.

You'll have to implement some level of custom tracking, even if you aren't creating custom events. In addition, you'll need to place your event logging calls (appier('event', ...)) into the relevant event handler functions.

For instance, if you run a media content site, and you have a handler function that runs when a new article is loaded, this is where you should log the event.

const event_parameters = {

'author': 'Chen Wei',

'topic': 'Tracking implementation',

'title': document.title,

'url': window.location.href

}

appier('event', 'article_viewed', event_parameters)Updated 23 days ago



Data Loader Overview

https://docs.airis.appier.com/docs/data-loader-overview



AIRIS's data loader offers the following features and benefits:

Data integrity: Relying on frontend or client-side tracking can often lose data due to various factors such as blockers or incorrect coding. Use AIRIS's data loader to establish a direct connection to your data source and maintain lossless data from your database or data source.

Historical data: While event-based tracking records data in real-time, there's no way to access historical data unless it was recorded previously. The data loader allows you import your historical data and make it available for immediate consumption and analysis.

No developer required: With traditional event tracking, you usually need a developer to code custom events on your website. With AIRIS's data loader, all you need is database credentials to start importing data. Setup is easy, and you can simply select what data you want to bring in — no coding required.

👍Data retentionAIRIS supports a minimum data retention period of 2 years. To increase your organization's data retention period, contact your customer success manager.

You can import data into AIRIS using the data loader in three different ways:

CSV Loader: Import a CSV directly from the AIRIS console.

Connections: Use one of AIRIS's third-party service integrations to import data to AIRIS.

Data stores: Use data imported from a CSV or connection to enrich existing AIRIS user profiles.

Cursor Guidelines [0]

https://docs.airis.appier.com/docs/suggested-cursor-list



AIRIS imports data in batches, i.e. one batch per sync interval, which is why a cursor is needed to mark the position at which one batch ends and the next should begin. Please refer to the following guidelines when selecting a cursor:

Use a unique cursor to avoid cursor collision: Since the cursor is used to determine where to start importing data for each sync interval, it's critical to choose a cursor that isn't likely to have a collision (duplicated values) within a data set.

Use a dynamic cursor to support upserts: AIRIS supports upsert operations to update existing data, which is accomplished by overwriting previously-imported data. For example, if your system implements logic to update product purchased events for users that later return the product, you can use upserts to retroactively update previously-imported data in AIRIS.

👍Recommended cursorWe recommend using a cursor that composed of a primary key for uniqueness combined with a dynamic field, e.g. the event's last updated timestamp, for upsert support.

Unexpected import behavior may occur if cursor values have collisions, meaning that multiple cursors share the same value. Because AIRIS uses the cursor to detect where to begin importing, duplicate cursor values may cause the import to start at the wrong position in the data set.

To avoid cursor collision issues, select a cursor that is as unique as possible. For example, if your cursor contains a database table's primary key, it will always be unique within a single table, guaranteeing that cursor collisions won't occur.

If you'd like to use upsert operations to update previously-imported data, don't use static fields like timestamps or counters for the cursor, otherwise data that has been imported once will never be imported again since the cursor has already moved past that position.

Instead, we recommend selecting a dynamic field that reflects the recency of the data, such as the last updated time. This allows you to update previously-imported events in future syncs.

Connect your AIQUA account.

Set the following trigger settings:

Performed by: Choose a user segment

Trigger when: Choose the user event that triggers the target action

Frequency: Choose how often the target actions should be executed

Next, set the following AIQUA settings:

Connection: Select the connected AIQUA account with the web push campaign.

Campaign ID: Enter the campaign ID of the web push campaign you'd like to send.

Under Map Fields, input the AIRIS field that should be mapped to the Appier ID. The Appier ID is used by AIQUA to uniquely identify users.

Finally, click Create to complete the creation process.
